# Binom v2: план интеграции витрины

Зафиксировано 08.10.2026 с учётом уточнения пользователя.

## Модель

- Поток — одна витрина с произвольным названием.
- «Оффер» в нашей админке — один баннер, а не сущность Offer в Binom.
- Каждый баннер связан с отдельной **Campaign** в Binom. Все его вариации идут в эту же кампанию.
- Копия баннера получает новые ID и пустую привязку кампании: под неё создаётся отдельная кампания.
- Лиды и апрувы берём из этой кампании, учитывая только переходы из витрины.

## Метки перехода

| Параметр URL | Значение | Для чего |
| --- | --- | --- |
| dm_source | domonetka | Отделить трафик витрины |
| dm_flow | постоянный ID потока | Определить витрину |
| dm_offer | постоянный ID баннера | Определить баннер |
| dm_variant | ID сочетания картинки, заголовка и описания | Сравнивать вариации |
| dm_click | новый UUID на каждый переход | Сверка отдельного перехода |

ID варианта уже стабилен при повторном сохранении тех же материалов. Названия, адреса потоков и порядок в сетке не используются как ключи статистики. UUID перехода хранится отдельно от суточных уникальных кликов для CTR. Метки добавляются только к баннеру с явно указанной кампанией. Совпадение с существующими dm_* параметрами отклоняется при сохранении, исходные query-параметры и fragment сохраняются.

В Binom нужен источник трафика с URL Parameter для каждой метки. Связать эти параметры со свободными token_1 … token_30. Номера токенов настраиваются, а не назначаются вслепую. External ID существующего источника не перезаписываем. Для API-отчёта достаточно token-вариации вместе с метками источника, потока и баннера; dm_click нужен для детальной сверки.

### Настройка существующих источников баеров

В редакторе баннера после указания Campaign ID открывается таблица с инструкциями. Для каждой метки баер добавляет свободный токен в **источнике именно этой кампании**, затем выбирает его номер из T1–T30. У каждой строки показаны Parameter (`dm_*`), Placeholder (оставить пустым, значения добавляет платформа) и Name (`Домонетка · …`). В Binom отключить добавление этих токенов в генерируемые Campaign URLs. Уже занятые токены и External ID не изменять.

Каждый пользователь задаёт свой адрес, API-ключ и токены в разделе Binom. Баннеры динамически наследуют токены владельца потока, даже когда их редактирует администратор. Администратор просматривает и редактирует настройки любого пользователя через Пользователи → Binom. Переключатель «Свои токены» у баннера включает локальное соответствие `binom_tokens`; его выключение возвращает наследование. При миграции все ранее заполненные соответствия сохранены как индивидуальные. Можно сохранить частичную настройку; сервер запрещает одинаковые номера, значения вне 1–30 и неизвестные метки. Для запроса отчёта клиент требует полную настройку и использует выбранные номера, а не фиксированные token_3 и т.п. Копирование баннера очищает Campaign ID и индивидуальные токены, возвращая наследование. Сохранённое соответствие пока считается заявленным пользователем, а не проверенным по API: проверка источника и параметров запланирована на подключение реального импорта.

### Общий адрес и API-ключ

Пользователь задаёт свой HTTPS-адрес трекера и API-ключ в разделе Binom; администратор может менять настройки каждого пользователя. Настройки приватно хранятся в `/opt/domonetka/data/binom-user-<sha256(user_id)>.json` с правами 600 и атомарной заменой файла. Ключ никогда не возвращается в ответы API, не появляется в URL и не доступен обычным пользователям. Пустое поле при сохранении оставляет прежний ключ; предусмотрено явное удаление. Смена адреса требует нового ключа или удаления старого, чтобы не переслать ключ другому трекеру случайно. Клиент не следует HTTP-редиректам с ключом.

Кнопка «Проверить сохранённое подключение» делает серверный GET `/public/api/v1/traffic_source/list/filtered?limit=1&offset=0` с `Api-Key`. В браузер возвращается только результат проверки, без данных трекера. Эта проверка подтверждает доступ к выбранному API-методу, а не корректность токенов или доступ ко всем кампаниям. Автоматический импорт пока не включён.

## Проверенная документация

Авторизованно прочитана документация конкретного трекера `https://nutrawellness.org/api/doc`. Сохранена статическая OpenAPI-схема без учётных данных: `docs/binom-v2-openapi.json`.

- Заголовок авторизации: `Api-Key`. Ключ пользователя наследует его права. [API v2](https://docs.binom.org/api-v2.php).
- `GET /public/api/v1/report/campaign`: `ids[]` = ID Campaign; `groupings[]` поддерживает `days`, `token_N`, `conversionStatusOne`, `conversionStatusTwo`; доступны `datePreset=custom_time`, `dateFrom`, `dateTo`, `timezone`, `limit`, `offset`. Ответ содержит `report`, leads, clicks, revenue и другие колонки.
- `GET /public/api/v1/report/campaign/groupings?campaignId=…`: доступные группировки и токены кампании.
- `GET /public/api/v1/traffic_source/{id}`: соответствие token ID → parameter.
- `GET /public/api/v1/conversions`: фильтр `campaignIds[]`, даты, timezone, cursor/from/to/direction и pageInfo. Ответ зависит от разрешённых колонок пользователя. Нельзя предполагать, что в нём доступны все токены.
- Статусы cnv_status/cnv_status2 и схемы статусов настраиваются в Binom. Апрув нельзя определять просто по payout > 0. [Статусы](https://docs.binom.org/status-scheme-v2.php), [токены источника](https://docs.binom.org/create-source-v2.php).

## Этапы

1. **Начальная реализация:** привязка Campaign ID в редакторе баннера; атрибуция переходов; постоянный журнал UUID кликов; диапазон дат и суточная статистика собственных показов/кликов; клиент чтения Binom по проверенным API-контрактам. Автоматические локальные проверки. Кампании трекера не изменять. По прямой просьбе пользователя 08.10.2026 этот этап опубликован для подготовки кампаний баерами.
2. **Пилот с пользователем:** выбрать одну новую кампанию и источник; определить свободные токены; прочитать доступные колонки и небольшой реальный ответ отчёта. Установить серверный API-ключ с минимально достаточными правами, не сохранять логин/пароль трекера в коде. Настроить явные значения статусов approved/pending/rejected по кампании; неизвестные показывать отдельно.
3. **Импорт:** адаптер реального ответа с пагинацией и проверкой группировок. Фильтровать одновременно dm_source, dm_flow, dm_offer, dm_variant. Хранить дневные снимки с кампанией и версией привязки; заменять снимок атомарно, не прибавлять повторно. Повторно читать предыдущие периоды для поздних апрувов. Отображать последнюю успешную синхронизацию, ошибку и отсутствие данных отдельно от нуля. Смена кампании не должна смешивать старую статистику с новой.
4. **Интерфейс результатов:** лиды, апрувы, отклоны, неизвестные статусы, CR и Approval Rate по баннеру и вариации, по датам. CR рассчитывать по кликам Binom; местные клики CTR дедуплицированы и не годятся для этого знаменателя. Рейтинг витрины пока оставить по CTR, смену критерия согласовать после набора данных.
5. **Сквозные тесты и выкладка:** два варианта одной кампании, другой баннер/кампания, другой поток; один лид с последующим апрувом, повторная синхронизация, поздний апрув, смена кампании, права разных пользователей. Сверить с Binom. Перед выкладкой сделать резервную копию БД и кода, обновить только сервис домонетки.

## Даты и границы достоверности

Существующие показы, посетители и клики записаны по UTC-дням без точного времени. Начальная разбивка явно использует UTC, Binom-запросы тоже UTC. Для перехода на другой часовой пояс нужна запись точного времени новых событий; старые события нельзя честно пересчитать.

Основной совместный отчёт планируется по **дате клика**: лиды и текущие статусы относятся к дню привлечения. На пилоте обязательно проверить, что группировка days в Binom соответствует этой модели. Дату создания конверсии и дату смены статуса нельзя смешивать с датой клика. Исторические переходы без меток невозможно восстановить до вариации достоверно.

Интервал предназначен для всей статистики Binom: косты, клики, лиды, текущие статусы,
апрувы, выручка и расчётные метрики. Пока адаптер импорта не подключён, расписание
