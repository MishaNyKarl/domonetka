Текущий production-клиент: opsvault-sso 0.1.2, commit
`08d057fd214d58d4210032916025566f5e1550c1`. SHA256 wheel:
`690d089239b93eb6cd005d98434ca415a55ca02af71fc7025a73bef1a39c04fb`.

## Конфигурация

systemd drop-in: `deploy/domonetka-sso.conf`. Конфиденциальные значения только
в `/etc/domonetka-sso.env`, root:root, 0600. EnvironmentFile имеет приоритет
над безопасным значением SSO_ENABLED=0 в drop-in.

Обязательны SSO_ENABLED, SSO_ISSUER, SSO_CLIENT_ID, SSO_CLIENT_SECRET,
SSO_SESSION_ENDPOINT, SSO_ACCESS_ENDPOINT, SSO_ENCRYPTION_KEY (Fernet).
SSO_JIT_ENABLED=1: первый вход нового разрешённого OpsVault subject создаёт
локальный аккаунт и сохраняет отдельный пароль в Vault. Требуется явный
центральный ServiceGrant; /our-services/ его автоматически не выдаёт.
SSO_LINK_TARGETS содержит адресные пары локальный ID → UUID/имя OpsVault:
admin → karlmichael, dima → DemiGO. Эти subjects зарезервированы для прежних
учёток и до explicit linking не могут создать дубликаты через JIT.
Цель проверяется при callback и повторно перед публикацией пароля/commit.
Идентификаторы доставлены RSA-OAEP и расшифрованы только в памяти; .env root 0600.
Legacy single-target параметры заменены адресным JSON map.
Redirect URI определяется только PUBLIC_ORIGIN:
`https://dop.afriro.online/auth/opsvault/callback`.
Ключ шифрования генерируется отдельно и не хранится вместе с DB backup.

## Текущая версия 0.1.2

09.10.2026: OpsVault CI 37861949913 и Deploy 37862541510 успешны.
Домонетка переключена на отдельный venv 0.1.2 после проверки discovery и
трёх конфиденциальных API: синтаксически корректный неизвестный UUID и
недействительный lease получили 403, записи реквизитов не создавались.
Health/config и соседний Binom отвечают успешно. Перед обновлением создана
копия кода и SQLite; три пользователя с прежними hash/flag, два потока,
девять баннеров и один трекер сохранили идентификаторы и владельцев.
В рабочем браузере проверен новый текст согласия. Связей по-прежнему ноль:
сохранение реквизитов, оба способа входа и импорт ожидают проверки владельцем.

45 изолированных тестов прошли с точным SDK 0.1.2; Python/JS/Bash и текст
согласия проверены. Это не подтверждает реальный пользовательский OIDC-вход.

Локальный пароль сохраняется при linking. Его отправка в OpsVault требует
явного текста в форме и save_credentials=true; старое окно не может начать
новый сценарий. До callback пароль зашифрован Fernet и привязан к state и
локальной сессии, срок действия не больше 300 секунд. После callback секрет
остаётся только в зашифрованном pending, с тем же общим сроком действия.
Подтверждение повторно проверяет прежний PBKDF2 внутри атомарного on_link,
публикует реквизиты по живому OIDC lease и только затем завершает linking.
Ошибка публикации откатывает локальную связь. Прежние ID/hash остаются,
все старые сессии завершаются.

Локальный вход связанному аккаунту создаёт отдельную policy-сессию:
/local-access/ сверяет issuer/subject/uid, роль и центральный service grant.
Вход и POST проверяются свежим запросом, GET использует кеш до 60 секунд.
Отказ завершает сессию; недоступность после истечения кеша даёт 503.
Выключенный SSO блокирует вход и импорт всех связанных аккаунтов,
независимо от local_login_enabled. Логин/пароль/локальную роль нельзя
редактировать обычной формой, чтобы не рассинхронизировать Vault и сервис.
Общий выход применяется к OIDC-сессиям; локальный вход закрывает свою сессию.

Для JIT get_credentials по живому lease восстанавливает канонические
ID/логин/пароль после успешной публикации и неудачного локального commit.
По имени/email по-прежнему нет автосвязывания; существующие локальные ID
требуют явного linking. Новый пароль случайный; в домонетке только PBKDF2,
в OpsVault зашифрованная запись с доступом владельца. JIT пока выключен.

## Первая версия 0.1.1 в production

Ниже описан прежний сценарий; версия 0.1.2 сохраняет локальный пароль.

- Миграция добавляет users.local_login_enabled и sessions.csrf, сохраняя
  первичные ключи и владельцев. Sidecar SQLiteStore добавляет ov_sso_*;
  хост добавляет зашифрованное краткосрочное подтверждение linking.
- JIT создаёт UUID и технический username. По имени/email аккаунты не ищутся.
  Локальный вход для SSO-пользователя запрещён, password_hash — маркер `!`.
- Связывание начинается из локальной сессии: пароль + CSRF, OIDC, отдельное
  явное подтверждение обоих аккаунтов. on_link в одной транзакции записывает
  связь, отключает пароль и удаляет прежние локальные/SSO-сессии.
- Каждый защищённый запрос проверяет центральную роль; POST проверяет её
  свежим запросом. Кеш — максимум 60 секунд, сбой после истечения даёт 503.
  Собственные проверки owner_id остаются. SSO-сессия не продлевается до 30 дней.
- Есть локальный и общий выход. При сбое общего выхода местная сессия закрывается,
  интерфейс сообщает, что общий выход не подтверждён.
- Фоновый импорт отдельно проверяет can_import перед HTTP-чтениями и перед
  сохранением. Если SSO отключён, импорт связанных аккаунтов тоже закрывается.
  Незавязанные аккаунты остаются локальными на переходном этапе.
- /auth/* исключены из Python access logs; callback использует no-referrer.
  Фактический Caddy site не содержит access logging.

## Откат

Перед миграцией — согласованная SQLite-копия и код. После linking не включать
старые пароли и не запускать старый воркер, обходящий центральные разрешения.
Отключение SSO_ENABLED блокирует вход и импорт уже связанных аккаунтов;
аварийный локальный администратор остаётся отдельно. Вернуть провайдер либо
согласованную версию кода/схемы, сохраняя данные после резервной копии.
